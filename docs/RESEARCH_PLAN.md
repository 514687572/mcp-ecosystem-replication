# Research plan

**Title**: The Model Context Protocol Server Ecosystem: An Empirical Study of
Quality, Security, and Evolution

**Target**: *Software: Practice and Experience*, Special Issue on AI-Native
Software Engineering (`SPE-SI-AINSE`), deadline **15 January 2027**.

**Fallback**: SPE regular issue; if rejected, JSS regular issue reframed around
"SE for AI systems".

## Research questions

**RQ1 — Interface design.** What interface design patterns do published MCP
servers exhibit, in tool granularity, naming, description quality, and input
schema declaration?

**RQ2 — Security posture.** How do servers handle credentials and remote
exposure, and where does the declared configuration diverge from safe practice?

**RQ3 — Evolution.** How does the ecosystem evolve: publish cadence, version
churn, abandonment, deprecation, and protocol/schema adoption?

**RQ4 — Inspectability.** How much of the ecosystem can be assessed from
machine-readable artefacts alone, and what does the remainder hide?

RQ4 is the study's methodological contribution and the reason it is more than a
census: it quantifies how much of an agent-tool ecosystem resists automated
audit, which matters to anyone building governance for agent tooling.

## Hypotheses to test

H1. Publishing activity is highly concentrated; a small set of namespaces
dominates version counts, so version counts are a misleading activity proxy.

H2. Hosted-only servers (remote endpoints, no package) dominate the population
and churn fewer versions than package-based servers.

H3. Credential-like configuration is frequently not flagged as secret, so
downstream clients cannot automatically redact it.

H4. Tool descriptions rarely state *when* a tool should be used, even though
tool selection depends on exactly that.

H5. A substantial share of servers cannot be assessed from machine-readable
artefacts (no repository, no package, no schema).

## Method

### Data

Primary source is the official MCP registry, harvested as a complete snapshot
through the freeze date in `config/config.yaml`. It publishes every version of
every server together with registry-side timestamps, which no other source
provides.

Enrichment:

* npm and PyPI metadata (licence, maintainers, deprecation, downloads)
* package source archives, for static tool-definition extraction
* GitHub repository metadata and releases, for declared-versus-actual activity

### Sampling

Tool extraction requires downloading package sources, so it runs on a random
sample drawn with a fixed seed from the population of latest-version npm and
PyPI packages. Both the seed and the drawn sample are stored under
`data/interim/`, so the analysed set is exactly reproducible.

### Analysis

All tables are generated by `scripts/02_analyze_registry.py` and
`scripts/06_cross_analysis.py` from the stored data. Nothing is computed by
hand.

Manual work is limited to two activities, both with a written codebook
(`docs/codebook.md`): validating tool extraction on a hand-checked subsample,
and coding the security-relevant design choices that resist automation.

## Threats to validity

See `docs/threats-to-validity.md`. The two that need the most care:

1. **Registry timestamps measure registry ingestion, not author intent.** A
   sub-day median gap between versions is an artefact of bulk publishing, not of
   human release practice. The paper must present it as such.
2. **Static tool extraction is partial.** Recall must be estimated on a manually
   checked subsample, and reported.

## Reporting obligations

* Freeze date stated in the abstract's method sentence and in every table caption.
* Population and sample sizes reported together, never the sample alone.
* Extraction recall reported next to every tool-level claim.
* Negative results reported explicitly: plaintext endpoints, bare IP endpoints,
  and localhost endpoints were all zero, which is a finding about the registry's
  validation, not about the ecosystem's discipline.
